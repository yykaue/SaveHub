# 游戏管理说明与验收

本次功能于 2026-11-04 在 Windows 开发运行环境验证。版本号仍为 1.1.4；源码和 `dist/` 包含本次功能，已有安装包、便携版和 GitHub Release 未重新构建或发布。验证全部使用 `.test-data` 下的合成资料库，未操作用户实际游戏存档。

## 页面与操作

侧栏「游戏管理」是独立管理入口，「全部游戏」继续保留原来的游戏概览。

管理页支持按名称或副标题搜索、添加、编辑、打开存档库、单游戏导出，以及勾选后导出所选或导出全部。列表显示本机游戏路径、全部记录数量和容量；此处数量包含普通存档、回收站记录及读档恢复点，因此可能大于存档库侧栏的普通存档数。

「已删除游戏」可以找回游戏配置和仍被保留的存档。管理页编辑配置后停留在管理页。

## 删除

确认框默认不勾选「一并永久删除该游戏的全部存档记录」。默认删除只隐藏游戏项目，保留记录和备份文件，之后可找回。

勾选后，确认按钮变为「删除游戏并永久删除存档」，并显示记录数量与物理删除说明。该操作删除当前游戏在 SaveHub 资料库中的整个存档区，包含普通、保护、收藏、回收站、恢复点、损坏记录，以及尚未清理的覆盖暂存文件和对应事务。保护标记不阻止这项明确的游戏级清理。其他游戏、导入源、已导出的副本和游戏原始存档目录不在清理范围。

永久清理失败时，游戏保留“存档永久清理未完成”的状态，不允许找回部分已删除的数据；管理页提供「重试永久清理」。下次启动也会继续这项已经确认的清理。正在清理的游戏不能作为游戏配置覆盖目标，旧覆盖事务不会把已确认删除的记录恢复回来。

## 导出

导出确认框默认不勾选「一并导出存档记录」，只导出名称、副标题、图标、配色、两套系统路径、备份项目和旧存档路径等配置。

勾选后，导出该游戏全部有效记录，保留名称、备注、创建时间、原平台、收藏与保护标记、回收站状态和恢复点分类，以及完整性清单。尚未完成单记录永久删除或损坏的记录会导致本次组合导出失败，不会悄悄遗漏后报告成功。

每次生成独立外层文件夹，同名时添加 ` (2)` 等后缀。文件先复制并校验，再发布；失败只清理本批拥有的输出，不覆盖已有导出或并发创建的目标。

```text
所选目录/
  游戏名-游戏导出/                 多游戏时为 SaveHub-游戏导出
    games.json                    游戏包清单
    游戏名/
      game.json                   配置、类型、版本及随包存档数量
      snapshots/                  仅有随包存档时存在
        存档名称/                  原始文件和目录
        .savehub-exports/
          collection.json         原有命名导出的存档元数据格式
```

`games.json` 的类型为 `savehub-games`，版本为 1；其中 `games` 是直接子目录列表。单游戏 `game.json` 的类型为 `savehub-game`，版本为 1，包含 `game`、`includesSnapshots`、`snapshotCount`。配置包和组合包使用同一格式，不需要压缩或解压工具。

## 导入与重复项

1. 点击「导入游戏」，选择完整外层文件夹，或其中含 `game.json` 的单游戏文件夹。
2. 按游戏标识、此前导入的来源标识或规范化名称识别重复。所有重复游戏在一个界面逐项选择，也可批量选择覆盖、跳过、两者并存；初始为跳过。
3. 「覆盖」只替换配置，保留目标游戏 ID、创建时间与全部现有存档；若目标已删除，会找回该游戏。「跳过」也跳过该游戏随包存档。「两者并存」创建独立游戏 ID 和不冲突的编号名称，随包存档进入该新游戏。
4. 点击「下一步：检查存档」，生成最终导入预览；此时仍没有写入配置或记录。各游戏的重复存档统一展示，沿用现有逐项和批量处理界面。
5. 存档「覆盖」保留目标 ID、创建时间和收藏标记，使用现有复制校验及覆盖事务回滚；保护、回收站、未完成清理、损坏记录和恢复点不能作为覆盖目标。可选择跳过或两者并存。
6. 最终点击「执行导入」才写入。任一步取消，包括关闭弹框和 Escape，都会作废本次计划，不执行新导入或覆盖。游戏配置结果和各游戏存档结果分别展示；文件复制失败可能表现为游戏配置已导入、个别存档导入失败，结果会明确列出。

导入计划由主进程保管并只能执行一次。确认前会检查游戏配置、重复目标状态、清单和存档内容是否变化，拒绝伪造、遗漏或重复的决策。组合包存档通过导出身份识别重复，移动整个包后再次导入仍能识别；同一来源已有多份存档时需指定覆盖目标。

随包记录保留来源平台和状态，即使本机尚未配置游戏存档路径也可导入。导入不会将备份写入游戏原始目录；使用「读档」前仍需在游戏设置中核对本机路径。单独使用原有「导入存档」的历史行为保持不变。

## 实现与验证

主要文件：`src/GameManagement.tsx`、`src/App.tsx`、`src/ImportDialog.tsx`、`electron/game-transfer.mjs`、`electron/storage.mjs`，以及对应 IPC、类型和中英文文案。现有存档导入拆分为共享的规划、决策校验、执行方法，游戏组合导入复用同一覆盖限制与替换事务。

可复现命令：

```powershell
npm test
npm run build
npm run test:games
npm run test:import
npm run test:deletion
npm run test:interactions
```

`pnpm` 的同名脚本等效。GUI 测试需要可正常启动 Electron 的 Windows 权限及当前 `dist/`；受限沙箱曾因 Electron 目录 ACL 拒绝启动，随后在正常 Windows 权限下完成验证。

- `npm run build`：TypeScript 与 Vite 通过。
- `test:games`：9 组实际 Electron 页面／preload／IPC 检查通过，无渲染错误；包含默认与勾选导出、默认与物理删除、两级取消、混合冲突处理、独立游戏并存、1060×720 最小窗口、四主题和英文。
