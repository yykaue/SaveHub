React, TypeScript, Vite, Playwright, and other dependencies are pinned in `package.json` and `pnpm-lock.yaml`. Do not opportunistically upgrade dependencies when setting up the environment.

First verify that the required CLI tools are available:

```powershell
Set-Location -LiteralPath 'C:\Users\Limbo\Desktop\SaveHub'
```

### 2.2 Install Dependencies

```powershell
pnpm install --frozen-lockfile
if ($LASTEXITCODE -ne 0) { throw 'Dependency installation failed; resolve errors before continuing.' }
```

`--frozen-lockfile` installs strictly from the existing lockfile and fails if `package.json` and `pnpm-lock.yaml` are out of sync. First-time installation downloads npm packages as well as the Electron binary runtime. `postinstall` runs the Electron install script; `pnpm-workspace.yaml` permits build scripts for Electron and esbuild.

Only update `package.json` and the lockfile when intentionally modifying dependencies, and review/commit them together. Never delete the lockfile just to bypass an install error. If `node_modules` is already complete and only the `pnpm` wrapper script is blocked in a restricted shell, you can invoke the direct local Node entry points listed in Section 12.

Verify that the Electron runtime binary is present:

```powershell
Get-Content -LiteralPath node_modules\electron\dist\version
Test-Path -LiteralPath node_modules\electron\dist\electron.exe
```

The paths above are for Windows, and the version must match the Electron version in `package.json`. If the runtime is missing, repair the installation first rather than treating missing dependencies as an application bug.

## 3. Directory Layout, Build Pipeline & Where to Edit

```text
React / TypeScript / CSS ── Vite ──> dist/
electron/main.mjs + preload.cjs + storage.mjs etc. ─┐
dist/ + build/icon.png + package.json ─────────────┴─ electron-builder
                                                       ├─ win-unpacked/resources/app.asar
                                                       ├─ Windows NSIS Installer / Portable EXE
                                                       └─ macOS arm64 DMG / ZIP
```

| Path | Responsibility & Maintenance Notes |
| --- | --- |
| `src/App.tsx` | Page coordination, game settings, save action callbacks, theme & language switching, and modals |
| `src/i18n/` | Frontend i18n locale dictionaries (`locales/zh.ts`, `locales/en.ts`), language registry, and typed translation helper |
| `src/format.ts` | Localized date formatting, preset game name mapping, and byte size formatting |
| `src/SnapshotList.tsx` | Tab scopes, search, sorting, multi-select, batch protection, and export |
| `src/RestorePoints.tsx` | Restore Points and Removed Restore Points actions |
| `src/ImportDialog.tsx` | Per-item duplicate import conflict resolution, batch quick-set, and import summary |
| `src/styles.css`, `src/list.css`, `src/themes.css` | Layout, list, and 4-theme styles; inspect all four themes and both languages when adding UI controls |
| `electron/main.mjs` | Main process, window management, native dialogs, application menu, and IPC sender validation |
| `electron/preload.cjs` | Exposes the explicitly enumerated `window.savehub` API to the renderer |
| `electron/storage.mjs` | Vault storage, SHA-256 copy verification, transactional recovery, import/export, and state rules |
| `electron/presets.mjs` | Default game presets and literal parser for legacy backup scripts |
| `tests/`, `scripts/` | Core unit/integration tests, real Electron GUI E2E suites, and release helper scripts |
| `build/` | **Source asset directory** containing packaging icons—not a disposable build cache |
| `dist/` | Production frontend bundle generated by Vite; never edit manually |
| `release/<version>/` | Packaged installers/binaries, SHA-256 digests, release notes, and verification evidence for that version |
| `.local-data/` | Development data library, retained across `pnpm dev` runs by default |
| `.test-data/` | Synthetic game files and temporary vaults created by automated GUI tests |
| `test-results/` | Current E2E reports, screenshots and traces in separate run directories; `docs/screenshots/` preserves historical records |

Main-process files under `electron/` are packaged directly without going through Vite compilation. After modifying `electron/*`, seeing new frontend asset hashes in `dist/` does not mean an existing EXE has been updated; you must repackage and audit `app.asar`.

Git tracks source code, tests, configuration files, lockfiles, `build/` icons, and hand-written Markdown documentation, while ignoring `node_modules/`, `dist/`, `release/`, local vaults, screenshots, and generated verification JSON files (see [`.gitignore`](../.gitignore)). Just because `release/` is git-ignored does not mean it can be deleted casually—it may hold the only local copy of delivered packages and acceptance evidence.

### Behavioral Invariants to Preserve During Development

- The renderer accesses filesystem and vault operations strictly through `preload.cjs` / IPC and never calls Node.js filesystem APIs directly. Windows run with `contextIsolation: true`, `sandbox: true`, and `nodeIntegration: false`.
- "Selected" batch actions operate on currently checked IDs; "All" batch actions operate on all records in the active tab regardless of search filter text. When modifying tab logic, check empty lists, mixed protection states, and records hidden by search.
- Records in the Recycle Bin must be recovered first before their protection flag can be modified; this restriction is enforced in both the UI and the storage layer.
- Every export creates a dedicated outer folder, duplicate names never overwrite existing files, and legacy export formats remain importable.
- Any change touching save payloads must preserve copy verification, automatic pre-restore Restore Point creation, failure rollback, and startup transaction recovery semantics.

## 4. Development & Local Run

### 4.1 Development Mode

```powershell
pnpm dev
```

This starts Vite (`127.0.0.1:5173`) alongside a real Electron window using `.local-data` in the project root. Renderer edits hot-reload via Vite; after editing main-process files or `preload.cjs`, close the window and re-run `pnpm dev`. Closing the Electron window terminates the dev server automatically, or you can press `Ctrl+C` in the terminal.

Vite is configured with `strictPort`: if port `5173` is already in use, it fails immediately rather than picking another port. Check whether another SaveHub dev server is already running before killing processes.

`pnpm dev:renderer` starts only Vite. Opening the URL in a regular web browser lacks the `window.savehub` bridge provided by Electron preload and cannot be used as a substitute for full application or save/restore testing.

### 4.2 Production UI Preview

```powershell
pnpm build
if ($LASTEXITCODE -ne 0) { throw 'Build failed.' }

$savedEnv = @{}
foreach ($key in @('SAVEHUB_DATA_DIR', 'SAVEHUB_DEV_URL', 'ELECTRON_RUN_AS_NODE')) {
    $savedEnv[$key] = [Environment]::GetEnvironmentVariable($key, 'Process')
}
try {
    $env:SAVEHUB_DATA_DIR = Join-Path (Get-Location).Path '.local-data\preview'
    Remove-Item Env:SAVEHUB_DEV_URL -ErrorAction SilentlyContinue
    Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
    pnpm start
    if ($LASTEXITCODE -ne 0) { throw 'Production UI preview failed.' }
}
finally {
    foreach ($key in $savedEnv.Keys) {
        [Environment]::SetEnvironmentVariable($key, $savedEnv[$key], 'Process')
    }
}
```

This runs the workspace Electron binary against your current source files and `dist/` to preview the production build; it is still not a packaged release binary. The snippet above uses an isolated preview vault and restores your environment variables upon exit.

Running `pnpm start` directly loads the existing `dist/index.html` without building first and without automatically isolating the data library like `pnpm dev` does. If `SAVEHUB_DATA_DIR` is not set, `pnpm start` will open your default `userData` library.

### 4.3 Running Packaged Binaries

On Windows, you can run the installer, portable executable, or `win-unpacked/SaveHub.exe` from the version directory under `release/`. When using the unpacked build, keep the **entire** `win-unpacked` folder together; copying `SaveHub.exe` alone will not work. Always close any running instance before launching a new version, and never kill the process in the middle of a backup, restore, or permanent deletion.

By default, the data library resides in Electron's `userData` folder: typically `%APPDATA%\SaveHub` on Windows and `~/Library/Application Support/SaveHub` on macOS (the exact path is shown in **Settings & About**). The portable executable only unpacks the application binaries into a temporary folder—**it does not automatically store the data library next to the portable EXE**. Set `SAVEHUB_DATA_DIR` explicitly if you want a custom vault location.

### 4.4 Environment Variables

| Variable | Purpose & Constraints |
| --- | --- |
| `SAVEHUB_DATA_DIR` | Overrides the data library directory; `pnpm dev` forces it to `.local-data` (overriding any caller value), and automated tests point it to isolated synthetic directories |
| `SAVEHUB_DEV_URL` | Tells an unpacked run to load the Vite dev server URL; set automatically by `scripts/dev.mjs`, cleared by GUI tests, and ignored by packaged builds |
| `ELECTRON_RUN_AS_NODE` | May be left set by external IDE/agent hosts; must be cleared when launching GUI windows (handled automatically by dev and test scripts) |
| `SAVEHUB_TEST_EXECUTABLE` | Points the UI, interaction, deletion, and import E2E suites at a specific packaged executable to verify; when unset, they launch the workspace Electron binary with current `dist/` |
| `SAVEHUB_KEEP_TEST_DATA` | Retains temporary `.test-data` folders after UI/interaction/deletion tests for debugging; any non-empty string enables it (including `0` or `false`), so remove the variable to disable |
| `SAVEHUB_PORTABLE_TEST_DATA` | Reuses and retains a dedicated test folder inside `.test-data` for portable EXE testing; never point it to a real user data library |
| `CSC_IDENTITY_AUTO_DISCOVERY` | Controls electron-builder certificate auto-discovery; set to `false` in CI so unsigned builds succeed without certificates |

Never allow multiple processes to share the same data library directory concurrently. Set environment variables in the current shell process and restore them afterward; do not assume Electron's main process automatically reads arbitrary `.env` files.

### 5.2 Full Source-Stage Verification

Close any running SaveHub test or dev windows before starting. Run the test suites serially so that any failure stops immediately:

```powershell
$previousTestExe = $env:SAVEHUB_TEST_EXECUTABLE
try {
    Remove-Item Env:SAVEHUB_TEST_EXECUTABLE -ErrorAction SilentlyContinue
    foreach ($task in @('test', 'build', 'test:ui', 'test:interactions', 'test:deletion', 'test:import')) {
        pnpm run $task
        if ($LASTEXITCODE -ne 0) { throw "Check failed: $task" }
    }
}
finally {
    $env:SAVEHUB_TEST_EXECUTABLE = $previousTestExe
}
```

To run the additional strict TypeScript unused-symbol check used in prior releases:

```powershell
node node_modules/@typescript/native/bin/tsc --noEmit --noUnusedLocals --noUnusedParameters
if ($LASTEXITCODE -ne 0) { throw 'Strict TypeScript check failed.' }
```

The GUI test suites launch real Electron windows via Playwright (not a headless web browser); all synthetic game files and vaults live under `.test-data` and never touch a user's real game progress. Core storage tests clean up their own temporary directories automatically; see Section 4.4 to keep GUI test data for inspection. The shared harness gives every run a unique artifact folder; the runner uses one worker to avoid concurrent desktop focus changes.

### 5.3 Reading Verification Reports

| Artifact | Contents |
| --- | --- |
| `test-results/source/runner/<case>/artifacts/<run>/` | Source runner reports, screenshots and trace archives |
| `test-results/package/runner/<case>/artifacts/<run>/` | Actual package reports; check executable, targets.version, targets.packaged and appPath |
| `test-results/e2e/<run>/` | Reports from individually invoked E2E scripts |
| `test-results/portable/<run>/` | Actual portable EXE report and trace |
| `test-results/installer/installation.json` | Installation, installed-application regression and uninstall result |
| `test-results/benchmark.json` | Summary cache and real-payload performance measurements |

Each harness run writes `run.json` with success, date, checks, rendererErrors, cleanupErrors and target identity. A passing result requires exit code 0 and a current successful report. Failed fixtures and diagnostic evidence are retained. `docs/screenshots/` contains historical evidence and is not a current-run signal. A source runtime report does not certify a packaged application.

## 6. Preparing a New Version & Windows Packaging

### 6.1 Version & Output Directory

First inspect pending changes and existing release directories:

```powershell
git status --short
git diff --stat
git diff --check
Get-ChildItem -LiteralPath release -Directory
```

Once the scope for the new release is finalized, update **both** fields in `package.json`:

| Field | Example for Next Patch Release |
| --- | --- |
| `version` | `1.1.5` |
| `build.directories.output` | `release/1.1.5` |

`1.1.5` is shown only as an example; changing `version` alone does not automatically update `build.directories.output`. When dependencies have not changed, you do not need to regenerate `pnpm-lock.yaml` solely for a version bump.

Before building a new release for the first time, verify that the target version directory does not already exist:

```powershell
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$releaseRelative = "release/$($pkg.version)"
if ($pkg.build.directories.output -ne $releaseRelative) {
    throw 'Version and build.directories.output do not match.'
}
if (Test-Path -LiteralPath $releaseRelative) {
    throw 'Target release directory already exists: check whether it is an incomplete current build or a historical deliverable before overwriting.'
}
```

Use this check when **starting a brand-new release version**; if you are resuming an interrupted build, follow Section 13 instead of deleting the directory. Historical released version directories must be preserved intact.

### 6.2 Windows Build Targets

```powershell
# When you only need the unpacked directory
pnpm pack:win
if ($LASTEXITCODE -ne 0) { throw 'Unpacked Windows build failed.' }
```

```powershell
# When building the NSIS installer and portable EXE (includes frontend build and win-unpacked)
pnpm dist:win
if ($LASTEXITCODE -ne 0) { throw 'Windows release packaging failed.' }
```

Choose either `pack:win` or `dist:win` depending on your goal; `dist:win` already produces `win-unpacked` so you do not need to run both back-to-back. All `pack:*` and `dist:*` scripts pass `--publish never` explicitly so that `electron-builder` only writes local artifacts and never attempts an implicit GitHub upload in CI environments when `GH_TOKEN` is absent. If invoking `electron-builder` directly via Node, always pass `--publish never`:

```powershell
pnpm build
if ($LASTEXITCODE -ne 0) { throw 'Build failed.' }
node node_modules/electron-builder/cli.js --win --x64 --publish never
if ($LASTEXITCODE -ne 0) { throw 'Windows release packaging failed.' }
```

Primary outputs under `release/<version>/`:

```text
release/<version>/
  SaveHub-<version>-win-x64.exe                 NSIS installer
  SaveHub-<version>-Windows-x64-portable.exe    Single-file portable executable
  win-unpacked/
    SaveHub.exe
    resources/app.asar
    ...                                         Complete unpacked Electron runtime files
```

The NSIS installer allows choosing the installation directory, creates shortcuts, and is configured with `deleteAppDataOnUninstall: false`. The `win-unpacked` directory is used for debugging packaging issues and running packaged GUI E2E suites; it is not a single-file portable binary.

### 6.3 Reusing the Locally Installed Electron Runtime

If your machine already has the exact pinned Electron runtime in `node_modules/electron/dist` and `electron-builder` hits a network error trying to download Electron again, you can pass `--config.electronDist`:

```powershell
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$installedElectron = (Get-Content -LiteralPath node_modules\electron\dist\version -Raw).Trim()
if ($installedElectron -ne $pkg.devDependencies.electron) {
    throw 'Local Electron runtime version does not match package.json.'
}
if (-not (Test-Path -LiteralPath node_modules\electron\dist\electron.exe)) {
    throw 'Local Electron executable is missing.'
}
node node_modules/electron-builder/cli.js --win --x64 --publish never --config.electronDist=node_modules/electron/dist
if ($LASTEXITCODE -ne 0) { throw 'Packaging with local Electron runtime failed.' }
```

Ensure `pnpm build` and `pnpm test` have already passed before running this command. Note that auxiliary tools such as NSIS may still be downloaded on first run if not cached locally. See the [electron-builder v26 configuration docs](https://www.electron.build/v26/docs/configuration/) for details.

## 7. Verifying Actual Release Packages

### 7.1 Unpacked Build & Portable Executable

After packaging completes, point `SAVEHUB_TEST_EXECUTABLE` to the packaged `win-unpacked\SaveHub.exe` binary and run the full GUI verification suites:

```powershell
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$releaseDir = (Resolve-Path -LiteralPath $pkg.build.directories.output).Path
$packedExe = Join-Path $releaseDir 'win-unpacked\SaveHub.exe'
if (-not (Test-Path -LiteralPath $packedExe)) { throw 'Unpacked executable not found.' }
$previousTestExe = $env:SAVEHUB_TEST_EXECUTABLE
try {
    $env:SAVEHUB_TEST_EXECUTABLE = $packedExe
    foreach ($task in @('test:ui', 'test:interactions', 'test:deletion', 'test:import')) {
        pnpm run $task
        if ($LASTEXITCODE -ne 0) { throw "Packaged GUI check failed: $task" }
    }
}
finally {
    $env:SAVEHUB_TEST_EXECUTABLE = $previousTestExe
}
```

Next, verify the single-file portable executable (which automatically locates the portable EXE from `package.json` rather than using `SAVEHUB_TEST_EXECUTABLE`):

```powershell
New-Item -ItemType Directory -Path docs\screenshots -Force | Out-Null
pnpm test:portable
if ($LASTEXITCODE -ne 0) { throw 'Portable executable verification failed.' }
```

`pnpm test:portable` verifies real NSIS unpacking and launch, version and UI assets, isolated backup creation and restoration, automatic Restore Point creation, and clean process termination via a test-only localhost debugging port.

### 7.2 Manual Installer Acceptance

Testing `win-unpacked` and the portable EXE does not replace testing the NSIS installer flow. Before distributing the installer, run it in a controlled Windows environment to verify custom install directory selection, desktop/Start Menu shortcuts, launched version, existing data library compatibility across upgrades, and data retention upon uninstall. Always use synthetic game directories for save/restore tests and document the machine, OS version, results, and any known limitations.

### 7.3 Generating SHA-256 Digests

After finalizing binaries, run:

```powershell
pnpm checksums
if ($LASTEXITCODE -ne 0) { throw 'Checksum generation failed.' }
```

The script reads the current version output directory and hashes its top-level EXE, DMG and ZIP files into UTF-8 `SHA256SUMS.txt`. Entries contain lowercase SHA-256, two spaces and the attachment basename, so the same file can verify downloaded release attachments. Runtime files inside unpacked applications are checked separately by the ASAR audit. Preserve historical version directories and their digests.

### 7.4 Release Audit & Evidence Archiving

```powershell
pnpm audit:release
if ($LASTEXITCODE -ne 0) { throw 'Release audit failed; do not proceed with delivery.' }
```

`scripts/audit-release.mjs` performs two checks:
1. Every runtime file in `electron/`, `shared/`, `dist/` (excluding compile-time `.d.ts` declarations), and the packaged build icons matches the SHA-256 digest of the corresponding file inside the platform-specific ASAR (Windows `win-unpacked/resources/app.asar` or macOS `mac-arm64/SaveHub.app/Contents/Resources/app.asar`), and the packaged `package.json` name, version, and main entry match.
2. Every file listed in `SHA256SUMS.txt` exists, is non-empty, and matches its recorded SHA-256 digest.

Upon success, it writes `docs/release-audit.json`. Note that running `pnpm audit:release` when source files have changed since the historical `1.1.4` build will intentionally fail because the current source differs from the historical `1.1.4` ASAR—build a new version directory rather than altering historical records.

After all tests and the release audit succeed, archive the verification evidence into the version directory:

```powershell
$ErrorActionPreference = 'Stop'
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$releaseDir = (Resolve-Path -LiteralPath $pkg.build.directories.output).Path
$evidenceDir = Join-Path $releaseDir 'verification'
New-Item -ItemType Directory -Path $evidenceDir -Force | Out-Null
Copy-Item -LiteralPath 'test-results' -Destination $evidenceDir -Recurse -Force
Copy-Item -LiteralPath 'docs/release-audit.json' -Destination $evidenceDir
$commit = git rev-parse HEAD
if ($LASTEXITCODE -ne 0) { throw 'Failed to read Git commit hash.' }
$state = git status --short
$sourceRecord = @("commit=$commit", "version=$($pkg.version)", "recorded=$(Get-Date -Format o)", 'git status --short:') + @($state)
$sourceRecord |
    Set-Content -LiteralPath (Join-Path $evidenceDir 'source-state.txt') -Encoding UTF8
```

Verify the timestamps and `executable` paths inside the JSON reports before archiving, and write `release/<version>/发布说明.md` along with `docs/验收记录-<version>.md`.

## 8. macOS Apple Silicon Build & Verification

On an Apple Silicon Mac, check out the exact same commit and lockfile with the same Node.js and pnpm versions. After completing the version preparation in Section 6.1, run:

```sh
pnpm install --frozen-lockfile || exit 1
pnpm test || exit 1
pnpm build || exit 1
pnpm test:ui || exit 1
pnpm test:interactions || exit 1
pnpm test:deletion || exit 1
pnpm test:import || exit 1
pnpm dist:mac || exit 1
```

The build configuration targets **arm64** DMG and ZIP archives only (no Intel builds). Output filenames follow `SaveHub-<version>-mac-arm64.dmg` and `SaveHub-<version>-mac-arm64.zip`.

After packaging, re-run the GUI test suites against the packaged `.app` by setting `SAVEHUB_TEST_EXECUTABLE` to `release/<version>/mac-arm64/SaveHub.app/Contents/MacOS/SaveHub`. Perform manual checks for DMG mounting, dragging to `/Applications`, first launch, game save directory permissions, backup/restore, restart persistence, and existing library loading, and record SHA-256 digests with `shasum -a 256`.

`build.mac.identity` is set to `"-"`, which applies an **ad-hoc signature** during packaging. Apple Silicon requires valid code signatures on executables; without ad-hoc signing, `electron-builder` bundle modifications invalidate the signature and cause Gatekeeper to report the downloaded app as "damaged". With ad-hoc signing, `codesign --verify --deep --strict --verbose=2 release/<version>/mac-arm64/SaveHub.app` passes, and users on other Macs can allow first launch via **System Settings → Privacy & Security → Open Anyway**.

Before distributing broadly to external macOS users, configure an Apple Developer ID certificate and notarization per the [electron-builder code signing guide](https://www.electron.build/v26/docs/features/code-signing/), and **remove `build.mac.identity: "-"`** (otherwise `"-"` overrides `CSC_NAME` / `CSC_LINK`). Store signing credentials in local keychains or CI Secrets—never in the repository.

## 9. Local Delivery & Remote Release

### 9.1 Local Delivery

Once source checks, packaged binary tests, and SHA-256 release audits pass, you can deliver the installer or portable executable along with the release notes, `SHA256SUMS.txt`, and acceptance record. If delivering `win-unpacked`, distribute or zip the **entire** `win-unpacked` directory rather than the standalone `SaveHub.exe`.

### 9.2 GitHub Release

Before publishing a GitHub Release, ensure all source and documentation changes are committed so the tagged commit matches the audited binaries. `release/` is git-ignored; upload installer and portable binaries as Release assets rather than committing binaries to Git.

Check repository, commit, and GitHub CLI authentication status:

```powershell
git remote -v
git status --short
git log -1 --oneline
gh auth status
```

Create and push an annotated version tag:

```powershell
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$tag = "v$($pkg.version)"
git tag -a $tag -m "SaveHub $($pkg.version)"
if ($LASTEXITCODE -ne 0) { throw 'Failed to create tag; check if the tag already exists.' }
git push origin HEAD
if ($LASTEXITCODE -ne 0) { throw 'Failed to push branch.' }
git push origin $tag
if ($LASTEXITCODE -ne 0) { throw 'Failed to push tag.' }
```

Publish the GitHub Release with `gh release create`:

```powershell
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$tag = "v$($pkg.version)"
$releaseDir = (Resolve-Path -LiteralPath $pkg.build.directories.output).Path
$releaseAssets = @(
    (Join-Path $releaseDir "SaveHub-$($pkg.version)-win-x64.exe")
    (Join-Path $releaseDir "SaveHub-$($pkg.version)-Windows-x64-portable.exe")
    (Join-Path $releaseDir 'SHA256SUMS.txt')
)
$notesFile = Join-Path $releaseDir '发布说明.md'
foreach ($file in ($releaseAssets + @($notesFile))) {
    if (-not (Test-Path -LiteralPath $file -PathType Leaf)) { throw "Missing release asset: $file" }
}
gh release create $tag @releaseAssets --verify-tag --title "SaveHub $($pkg.version)" --notes-file $notesFile
if ($LASTEXITCODE -ne 0) { throw 'Failed to create or upload GitHub Release.' }
gh release view $tag
```

Add `--draft` if you wish to review the release on GitHub before publishing. After uploading, download the release assets and verify their SHA-256 checksums against `SHA256SUMS.txt`.

SaveHub does not include an in-app auto-updater; users upgrade by closing the old version and installing or opening the new version.

## 10. CI Capabilities & Boundaries

PRs run lint, format, contract, typecheck/build, unit tests and smoke/retention UI tests on Windows. Main branches and tags add full source and packaged regression, Windows x64 and native macOS arm64 builds, portable/APFS checks, SHA-256 generation and ASAR audits. Failed runs upload evidence with always(). Only the tag draft-release job has contents: write. No Intel Mac job exists. Workflow configuration is not remote execution evidence.

## 11. Data Library Backup, Upgrade & Rollback

Before upgrading, close SaveHub, check the data library path in **Settings & About**, and back up the entire directory (including `library.json`, `library.json.previous`, `vault/`, and any `transactions/` folder). Backing up only the application installation folder or EXE does not back up your game save vault.

1.1.5 keeps the disk format versions but introduces 5/15 default retention and modification timestamps. Zero means no retention; old maxRestorePoints is replaced. Missing updatedAt falls back to creation time and persists on the next mutation. Startup enforces the effective limits after transaction recovery; read the README retention rules before upgrading.

If rolling back to an older application version, keep both version folders, close the running app, and launch the verified older executable. Rolling back the application binary does not automatically undo save/restore operations already performed on your game files.

Exported folders must retain their `.savehub-exports` subdirectory to preserve save names, notes, badges, and SHA-256 checksum manifests upon re-import. However, exporting saves is not a full backup of your application library (game path configurations, themes, language preferences, and unexported records still require backing up the data library folder).

## 12. Troubleshooting & Local Notes

| Symptom | Resolution |
| --- | --- |
| `pnpm` / `npm` not found or PowerShell `.ps1` execution policy error | Check `PATH` and Node installation; in PowerShell with restricted execution policy, invoke `pnpm.cmd` or `cmd /c "pnpm ..."`, or use the direct `node` entry points below |
| `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY` | Verify whether `node_modules` is already complete before forcing a reinstall; never blindly set `CI=true` to wipe modules if network access is restricted |
| Electron download `RequestError` / `AggregateError` | Check network connectivity or mirror settings; if the exact Electron version is already in `node_modules/electron/dist`, use `--config.electronDist` per Section 6.3 |
| `ELECTRON_RUN_AS_NODE` prevents GUI window from opening | Clear `ELECTRON_RUN_AS_NODE` in the current shell environment (handled automatically by dev and test scripts) |
| Port `5173` already in use | Check for an already-running Vite dev server from this project and stop the duplicate process |
| App still shows old UI / old version after code changes | Check which EXE you launched, whether `SAVEHUB_TEST_EXECUTABLE` is still set, or whether you only ran `pnpm build` without repackaging |
| `Packaged source differs` in `audit:release` | Current source / `dist/` no longer matches the packaged `app.asar`; rebuild and repackage for the target version rather than altering checksums |
| CI fails at the end of `dist:*` asking for `GH_TOKEN` | Ensure `--publish never` is passed to `electron-builder` (already included in all `pack:*` and `dist:*` scripts) |
| Data library remains after uninstalling or deleting portable EXE | By design, user data (`userData`) is stored separately from application binaries so upgrades and uninstalls never wipe user save backups |

## 13. Interruption Recovery & Final Checklist

When resuming after an interrupted session or command, first inspect the current workspace state:

```powershell
git status --short
git diff --stat
git diff --check
Get-ChildItem -LiteralPath test-results -Filter 'run.json' -Recurse -File |
    Select-Object Name,Length,LastWriteTime
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
if (Test-Path -LiteralPath $pkg.build.directories.output) {
    Get-ChildItem -LiteralPath $pkg.build.directories.output -File |
        Select-Object Name,Length,LastWriteTime
}
```

Review previous logs, verification JSON timestamps, and `git diff` before re-running steps. Retain valid evidence for completed steps whose inputs have not changed, and never wipe `release/` or `.local-data/`.

Every release delivery should satisfy the following checklist:

- Version number, `build.directories.output`, and Git commit are consistent, and release notes match the actual changes.
- TypeScript checks, core storage/import tests, production frontend build, and all GUI E2E suites pass; any code change re-runs affected verification suites.
- Actual packaged binaries have been runtime-verified, and JSON reports record the packaged executable path; any unverified installer or platform steps are explicitly noted.
- Windows `app.asar` matches current source / frontend build outputs, and all final artifact SHA-256 digests match `SHA256SUMS.txt`; macOS packages record their own verification results separately.
- Digests, release notes, screenshots, and verification JSON reports are archived under `release/<version>/verification/`, while historical releases and user data libraries remain intact.
