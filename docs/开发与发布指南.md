## 2. 环境准备

### 2.1 工具版本

| 工具 | 项目要求 | 说明 |
| --- | --- | --- |
| Node.js | `>=22.12.0`，建议 24 | CI 使用 Node.js 24 |
| pnpm | **11.25.0** | 与 `packageManager`、CI 保持一致 |
| Git | 用于版本管理 | 构建本地文件不需要远程仓库，远程发布需要另行配置 |
| Electron | 45.1.0 | 由项目依赖安装，无需全局安装 |
| electron-builder | 26.18.0 | 使用项目内版本，避免全局版本改变打包行为 |
| 构建主机 | Windows x64 / macOS Apple Silicon | Windows 包在 Windows 验证；macOS 包在 Mac 构建与验证 |

React、TypeScript、Vite、Playwright 等版本已经固定在 `package.json` 和 `pnpm-lock.yaml` 中。准备环境时不顺便升级依赖。

先检查命令是否可用：

```powershell
Set-Location -LiteralPath 'C:\Users\Limbo\Desktop\SaveHub'
Get-Command node,pnpm,git
node --version
pnpm --version
git status --short
```

若尚未安装 pnpm，可在具备 npm 的 Node.js 环境执行 `npm install --global pnpm@11.25.0`，然后重新检查版本。项目固定版本优先于官网展示的最新版本；其他安装途径见 [pnpm 官方安装说明](https://pnpm.io/installation)。

### 2.2 安装依赖

```powershell
pnpm install --frozen-lockfile
if ($LASTEXITCODE -ne 0) { throw '依赖安装失败，先处理错误再继续。' }
```

`--frozen-lockfile` 用于按已有锁文件安装，配置与锁文件不一致时会失败。首次安装需要下载依赖与 Electron 运行时。`postinstall` 会执行 Electron 安装脚本；`pnpm-workspace.yaml` 允许 Electron、esbuild 的构建步骤。

只有明确修改依赖时才更新 `package.json` 和锁文件，并一起检查、提交。不要为了绕过安装错误删除锁文件。若依赖已经完整可用、只有受管环境中的 pnpm 包装器异常，可使用第 12 节列出的本地 Node 入口继续验证。

检查 Electron 运行时是否完整：

```powershell
Get-Content -LiteralPath node_modules\electron\dist\version
Test-Path -LiteralPath node_modules\electron\dist\electron.exe
```

以上路径针对 Windows，版本应与 `package.json` 中的 Electron 版本一致。运行时缺失时先修复安装，不能把缺失依赖当作应用故障。

## 3. 目录、构建链路与修改位置

```text
React / TypeScript / CSS ── Vite ──> dist/
electron/main.mjs + preload.cjs + storage.mjs 等 ─┐
dist/ + build/icon.png + package.json ──────────┴─ electron-builder
                                                   ├─ win-unpacked/resources/app.asar
                                                   ├─ Windows 安装版 / 便携版
                                                   └─ macOS arm64 DMG / ZIP
```

| 路径 | 职责与维护方式 |
| --- | --- |
| `src/App.tsx` | 页面协调、游戏配置、存档操作回调、主题与语言切换及弹窗 |
| `src/i18n/` | 前端 i18n 多语言字典（`locales/zh.ts`、`locales/en.ts`）、语言注册表与类型安全翻译函数 |
| `src/format.ts` | 多语言日期、预设游戏名与文件大小格式化 |
| `src/SnapshotList.tsx` | 标签页范围、搜索、排序、勾选、批量保护与导出 |
| `src/RestorePoints.tsx` | 读档恢复点及已移除恢复点的操作 |
| `src/styles.css`、`src/list.css`、`src/themes.css` | 布局、列表和四主题样式；新增操作需检查四套主题 |
| `electron/main.mjs` | 主进程、窗口、原生对话框、IPC 来源验证 |
| `electron/preload.cjs` | 向页面暴露明确列举的 `window.savehub` API |
| `electron/storage.mjs` | 存储、复制校验、事务恢复、导入导出及状态规则 |
| `electron/presets.mjs` | 测试 fixture 辅助和显式旧脚本文本解析；生产启动使用空库 |
| `tests/`、`scripts/` | 核心测试、真实 Electron 交互测试、开发与发行辅助脚本 |
| `build/` | **源素材目录**，包含打包图标，不是可以整体清理的构建缓存 |
| `dist/` | Vite 生成的生产页面；不手工修改 |
| `release/<版本>/` | 打包产物、摘要、发布说明与该版本验收证据 |
| `.local-data/` | 开发资料库，默认跨开发启动保留 |
| `.test-data/` | 自动化测试的合成游戏文件与临时资料库 |
| `test-results/` | 本轮 E2E 报告、截图和 trace 按运行分目录；`docs/screenshots/` 保留历史记录 |

主进程文件直接随包分发，不经过 Vite 编译。修改主进程后，仅查看新的前端资源文件名不能证明 EXE 已更新；必须重新打包并审计 `app.asar`。

Git 应跟踪源码、测试、配置、锁文件、`build/` 图标和手写 Markdown 文档；忽略依赖、`dist/`、`release/`、本地资料库、截图和生成的验收 JSON。规则见 [`.gitignore`](../.gitignore)。发行目录被忽略不代表可以随意删除，其中可能包含唯一的已交付包与验收证据。

### 开发时需保持的行为约定

- 页面通过 preload / IPC 访问存储能力，不直接调用 Node 文件 API。窗口启用上下文隔离与沙箱，关闭 Node integration。
- “所选”操作使用当前勾选 ID；“全部”操作使用当前标签页的完整记录集合，不受搜索文本影响。修改标签页逻辑时同步检查空列表、混合保护状态和搜索隐藏记录。
- 回收站中的记录必须先找回才能修改保护标记；限制同时存在于界面和存储层。
- 所有导出包含独立外层文件夹，重名不能覆盖旧内容，旧导出格式继续可导入。
- 涉及存档内容的修改要保持复制校验、恢复前自动保存、失败回滚与中断恢复的既有语义。

## 4. 开发与本地运行

### 4.1 开发模式

```powershell
pnpm dev
```

该命令启动 Vite（`127.0.0.1:5173`）和真实 Electron 窗口，使用项目根目录下的 `.local-data`。渲染层修改由 Vite 热更新；修改主进程或 preload 后关闭并重新运行命令。关闭 Electron 窗口后开发服务会随之结束，也可在终端按 Ctrl+C。

端口设置为 `strictPort`：5173 被占用时直接报错，不会换一个端口。先确认是否已有开发服务运行，不要随意终止不相关进程。

`pnpm dev:renderer` 只启动 Vite。普通浏览器没有 Electron preload 提供的 `window.savehub`，不能用它代替完整应用或存读档验收。

### 4.2 生产界面预览

```powershell
pnpm build
if ($LASTEXITCODE -ne 0) { throw '构建失败。' }

$savedEnv = @{}
foreach ($key in @('SAVEHUB_DATA_DIR', 'SAVEHUB_DEV_URL', 'ELECTRON_RUN_AS_NODE')) {
    $savedEnv[$key] = [Environment]::GetEnvironmentVariable($key, 'Process')
}
try {
    $env:SAVEHUB_DATA_DIR = Join-Path (Get-Location).Path '.local-data\preview'
    Remove-Item Env:SAVEHUB_DEV_URL -ErrorAction SilentlyContinue
    Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue
    pnpm start
    if ($LASTEXITCODE -ne 0) { throw '生产界面预览失败。' }
}
finally {
    foreach ($key in $savedEnv.Keys) {
        [Environment]::SetEnvironmentVariable($key, $savedEnv[$key], 'Process')
    }
}
```

这里运行的是项目依赖中的 Electron 加当前源码和 `dist/`，用于检查生产页面；它仍不是发行包。示例使用独立预览资料库，并在退出后恢复原环境变量。

直接执行 `pnpm start` 会读取已经存在的 `dist/index.html`，不会先构建，也不会像 `pnpm dev` 一样自动隔离资料库。未设置 `SAVEHUB_DATA_DIR` 时，它可能打开正常使用的资料库。

### 4.3 运行已打包应用

Windows 可打开相应版本目录中的安装版、便携版或 `win-unpacked/SaveHub.exe`。解包版需要保留**整个** `win-unpacked` 文件夹；单独复制其中的 EXE 无法形成完整应用。运行新版前关闭旧版，尤其不要在备份、恢复或永久删除过程中结束进程。

默认资料库使用 Electron `userData`：Windows 通常为 `%APPDATA%\SaveHub`，macOS 通常为 `~/Library/Application Support/SaveHub`；以应用“设置与关于”显示的实际路径为准。便携版只把运行程序临时解包，**不会自动把资料库放在便携 EXE 旁边**。需使用独立资料库时显式设置 `SAVEHUB_DATA_DIR`。

### 4.4 环境变量

| 变量 | 作用与限制 |
| --- | --- |
| `SAVEHUB_DATA_DIR` | 指定资料库目录；开发启动脚本固定设为 `.local-data`，覆盖调用者给它的同名值；自动化测试设为自己的合成目录 |
| `SAVEHUB_DEV_URL` | 未打包运行时选择开发页面；开发脚本自动设置，GUI 测试主动清除；已打包应用忽略它 |
| `ELECTRON_RUN_AS_NODE` | 外部工具环境可能遗留；运行 GUI 应清除；开发及测试脚本已处理 |
| `SAVEHUB_TEST_EXECUTABLE` | 为 UI、交互、删除测试指定真正要验证的应用可执行文件；不设置时运行项目 Electron 和当前 `dist/` |
| `SAVEHUB_KEEP_TEST_DATA` | UI、交互、删除测试保留临时目录用于排错；任何非空字符串都启用，包括 `0`、`false`；取消应删除变量 |
| `SAVEHUB_PORTABLE_TEST_DATA` | 便携版测试复用并保留 `.test-data` 内的专用测试目录；与上一变量不同，不可指向真实资料库 |
| `CSC_IDENTITY_AUTO_DISCOVERY` | electron-builder 签名发现配置；现有 CI 设为 `false`，不代表已完成正式发行签名 |

不要让多个进程共用同一资料库。变量用当前终端的进程环境设置，修改后注意恢复；不能假定把这些变量写进任意 `.env` 文件就会被 Electron 主进程加载。

### 5.2 源码阶段的完整检查

运行前关闭占用同一项目的旧测试或开发窗口。以下脚本串行执行，任意步骤失败立即停止：

```powershell
$previousTestExe = $env:SAVEHUB_TEST_EXECUTABLE
try {
    Remove-Item Env:SAVEHUB_TEST_EXECUTABLE -ErrorAction SilentlyContinue
    foreach ($task in @('test', 'build', 'test:ui', 'test:interactions', 'test:deletion', 'test:import')) {
        pnpm run $task
        if ($LASTEXITCODE -ne 0) { throw "检查失败：$task" }
    }
}
finally {
    $env:SAVEHUB_TEST_EXECUTABLE = $previousTestExe
}
```

需要与此前发行相同的额外严格检查时执行：

```powershell
node node_modules/@typescript/native/bin/tsc --noEmit --noUnusedLocals --noUnusedParameters
if ($LASTEXITCODE -ne 0) { throw '额外 TypeScript 检查失败。' }
```

GUI 测试通过 Playwright 启动 Electron，不是网页浏览器测试；合成游戏文件和资料库均位于 `.test-data`，不操作用户的真实游戏进度。核心测试自行清理其临时目录；GUI 测试的保留开关见第 4.4 节。公共 harness 为每次运行分配独立产物目录；runner 使用单 worker，避免桌面焦点干扰。

### 5.3 如何读取测试结果

| 产物 | 内容 |
| --- | --- |
| `test-results/source/runner/<用例>/artifacts/<运行>/` | 源码 runner 的报告、截图和 trace |
| `test-results/package/runner/<用例>/artifacts/<运行>/` | 实际包报告；核对 executable、targets.version、targets.packaged 和 appPath |
| `test-results/e2e/<运行>/` | 单独执行 E2E 脚本的报告 |
| `test-results/portable/<运行>/` | 真实便携 EXE 的报告与 trace |
| `test-results/installer/installation.json` | 安装、已安装程序回归与卸载结果 |
| `test-results/benchmark.json` | 摘要缓存和真实 payload 的性能测量 |

公共报告 `run.json` 包含 success、date、checks、rendererErrors、cleanupErrors 和程序身份。成功需命令退出码为 0、报告属于本轮且 success 为 true；失败时保留 fixture 和诊断证据。`docs/screenshots/` 是历史证据目录，不能代表本轮执行结果。源码运行时的通过结果不能证明实际发布包通过。

## 6. 准备新版本与 Windows 打包

### 6.1 版本与输出目录

先查看待发布修改与已有发行物：

```powershell
git status --short
git diff --stat
git diff --check
Get-ChildItem -LiteralPath release -Directory
```

确认本次功能范围后，在 `package.json` **同时修改**：

| 字段 | 下一次补丁发行示例 |
| --- | --- |
| `version` | `1.1.5` |
| `build.directories.output` | `release/1.1.5` |

`1.1.5` 只是下一版本的示例，本文没有替项目升级版本。仅改 `version` 不会自动更新输出目录。当前锁文件根项目不记录版本号；依赖未变时无需仅为版本号重写锁文件。

首次打包前检查新目录尚未存在：

```powershell
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$releaseRelative = "release/$($pkg.version)"
if ($pkg.build.directories.output -ne $releaseRelative) {
    throw '版本号与发行输出目录不一致。'
}
if (Test-Path -LiteralPath $releaseRelative) {
    throw '该发行目录已存在：先确认是本轮未完成产物还是历史交付，不能直接覆盖。'
}
```

这段检查用于**开始一个新版本**；若正在恢复中断打包，按第 13 节判断已完成位置，不必删除目录重来。已经发布过的同版本文件应保留，新变化使用新版本。

### 6.2 两种 Windows 输出

```powershell
# 只需要解包目录时
pnpm pack:win
if ($LASTEXITCODE -ne 0) { throw '解包版构建失败。' }
```

```powershell
# 准备安装版和便携版时；已包含前端构建，不必先单独 pack:win
pnpm dist:win
if ($LASTEXITCODE -ne 0) { throw 'Windows 发行打包失败。' }
```

以上是二选一的用途，不要求连续执行。`pack:*` / `dist:*` 脚本都显式带 `--publish never`：项目没有远程发布配置，打包只生成本地产物。electron-builder 26 在 CI 环境（非 Pull Request）且未指定 `--publish` 时会隐式尝试发布并要求 `GH_TOKEN`，导致产物已生成、命令却以非零状态退出；本机没有 CI 环境变量，不会遇到。绕过 pnpm 包装器直接调用 builder 时，同样需要带上该参数：

```powershell
pnpm build
if ($LASTEXITCODE -ne 0) { throw '构建失败。' }
node node_modules/electron-builder/cli.js --win --x64 --publish never
if ($LASTEXITCODE -ne 0) { throw 'Windows 发行打包失败。' }
```

以版本号 `<版本>` 表示的主要输出：

```text
release/<版本>/
  SaveHub-<版本>-win-x64.exe                 NSIS 安装版
  SaveHub-<版本>-Windows-x64-portable.exe    单文件便携版
  win-unpacked/
    SaveHub.exe
    resources/app.asar
    ...                                    Electron 完整运行文件
```

安装版允许选择安装目录并创建桌面快捷方式，配置为卸载时不删除应用数据。解包版用来定位打包问题和执行包内 GUI 测试；它不是只含一个 EXE 的便携分发形式。其他 builder 中间文件、日志和 blockmap 按实际输出保留，不作为应用已具备自动更新的证据。

### 6.3 使用已安装的 Electron 运行时

在本机已安装正确版本运行时、builder 再次下载失败的情况下，可使用本地运行时：

```powershell
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$installedElectron = (Get-Content -LiteralPath node_modules\electron\dist\version -Raw).Trim()
if ($installedElectron -ne $pkg.devDependencies.electron) {
    throw '本地 Electron 与项目固定版本不一致。'
}
if (-not (Test-Path -LiteralPath node_modules\electron\dist\electron.exe)) {
    throw '本地 Electron 可执行文件缺失。'
}
node node_modules/electron-builder/cli.js --win --x64 --publish never --config.electronDist=node_modules/electron/dist
if ($LASTEXITCODE -ne 0) { throw '使用本地 Electron 打包失败。' }
```

前置条件仍是当前源码的构建和测试通过。这个参数只指定 Electron 来源，不能修复其他依赖缺失，也不保证首次打包完全离线；NSIS 等辅助工具可能仍需下载。该方式已用于本机 1.1.4 Windows 打包。配置含义见 [electron-builder v26 配置文档](https://www.electron.build/v26/docs/configuration/)。

## 7. 验证实际发行包

### 7.1 解包版与便携版

打包成功后，用版本配置定位真正的解包版，再执行与源码阶段相同的 GUI 检查：

```powershell
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$releaseDir = (Resolve-Path -LiteralPath $pkg.build.directories.output).Path
$packedExe = Join-Path $releaseDir 'win-unpacked\SaveHub.exe'
if (-not (Test-Path -LiteralPath $packedExe)) { throw '解包版不存在。' }
$previousTestExe = $env:SAVEHUB_TEST_EXECUTABLE
try {
    $env:SAVEHUB_TEST_EXECUTABLE = $packedExe
    foreach ($task in @('test:ui', 'test:interactions', 'test:deletion', 'test:import')) {
        pnpm run $task
        if ($LASTEXITCODE -ne 0) { throw "发行包检查失败：$task" }
    }
}
finally {
    $env:SAVEHUB_TEST_EXECUTABLE = $previousTestExe
}
```

随后测试单文件便携版。它会从当前版本目录选择便携 EXE，不使用 `SAVEHUB_TEST_EXECUTABLE`：

```powershell
New-Item -ItemType Directory -Path docs\screenshots -Force | Out-Null
pnpm test:portable
if ($LASTEXITCODE -ne 0) { throw '便携版验证失败。' }
```

便携版检查包括实际解包启动、当前版本与页面资源、隔离的创建存档与读档、自动保存原进度以及退出。测试以本机调试端口连接窗口，调试参数仅用于测试。

### 7.2 安装版手动验收

解包版和便携版测试不等于 NSIS 安装流程测试。正式分发安装版时，在可控的 Windows 测试环境执行安装，验证自选目录、快捷方式、启动版本、升级后资料库读取以及卸载后的数据保留。存读档操作使用合成游戏路径；记录机器、系统、版本、结果和已知限制。

1.1.4 的安装版已生成并校验摘要，**当时没有执行实际安装流程**。不要把这一项写成已经通过。

### 7.3 生成 SHA-256 摘要

发行文件最终固定后执行：

```powershell
pnpm checksums
if ($LASTEXITCODE -ne 0) { throw '生成摘要失败。' }
```

脚本读取当前版本输出目录，对顶层 EXE、DMG、ZIP 生成 UTF-8 的 `SHA256SUMS.txt`。每行为小写 SHA-256、两个空格及附件文件名，下载附件后可直接核验。解包目录中的运行文件由 ASAR 审计单独核对。保留历史版本目录及其摘要，不重写历史结果。

### 7.4 审计与归档

```powershell
pnpm audit:release
if ($LASTEXITCODE -ne 0) { throw '发行审计失败，不能继续交付。' }
```

审计核对当前运行源码、前端产物、图标与平台对应的 ASAR，以及包内名称、版本、入口；再验证所有附件摘要。仅编译时使用的 `.d.ts` 不纳入运行包比对。成功后写入 `docs/release-audit.json` 和版本目录中的 `audit-<平台>-<架构>.json`。

先运行 `pnpm checksums` 生成摘要，再运行审计。审计覆盖 electron、shared、dist 和构建图标，并根据当前平台定位 Windows 或 macOS arm64 ASAR；不替代安装、签名或实机验证。

本轮所有测试和审计成功后，将证据归档到版本目录：

```powershell
$ErrorActionPreference = 'Stop'
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$releaseDir = (Resolve-Path -LiteralPath $pkg.build.directories.output).Path
$evidenceDir = Join-Path $releaseDir 'verification'
New-Item -ItemType Directory -Path $evidenceDir -Force | Out-Null
Copy-Item -LiteralPath 'test-results' -Destination $evidenceDir -Recurse -Force
Copy-Item -LiteralPath 'docs/release-audit.json' -Destination $evidenceDir
$commit = git rev-parse HEAD
if ($LASTEXITCODE -ne 0) { throw '读取 Git 提交失败。' }
$state = git status --short
$sourceRecord = @("commit=$commit", "version=$($pkg.version)", "recorded=$(Get-Date -Format o)", 'git status --short:') + @($state)
$sourceRecord |
    Set-Content -LiteralPath (Join-Path $evidenceDir 'source-state.txt') -Encoding UTF8
```

归档前核对每份报告的时间与被测程序，删除或排除本轮未产生的旧截图，不能只凭同名文件存在判断成功。发布包应对应明确的已提交代码；若 `source-state.txt` 记录有未提交修改，先处理版本归属再对外发布。

编写 `release/<版本>/发布说明.md` 和可提交的 `docs/验收记录-<版本>.md`：说明实际变更、平台、文件名、测试结果、签名和安装验证状态、升级方式、已知问题。历史记录继续保留。E2E 的截图、run.json 和 trace 位于 test-results 的分次目录，实际包证据独立保存；版本目录继续归档本次结果。

## 8. macOS Apple Silicon 构建与验收

在 Apple Silicon Mac 检出相同源码和锁文件，安装相同 Node / pnpm 版本。先完成第 6.1 节的版本准备。以下为 Mac 终端示例，任意步骤失败时停止：

```sh
pnpm install --frozen-lockfile || exit 1
pnpm test || exit 1
pnpm build || exit 1
pnpm test:ui || exit 1
pnpm test:interactions || exit 1
pnpm test:deletion || exit 1
pnpm test:import || exit 1
pnpm dist:mac || exit 1
```

配置只包含 **arm64** 的 DMG 和 ZIP，不生成 Intel 版本。默认文件名形如 `SaveHub-<版本>-mac-arm64.dmg`、`SaveHub-<版本>-mac-arm64.zip`，以实际输出为准。

还应在打包后的 `.app` 上重跑 GUI 测试，把 `SAVEHUB_TEST_EXECUTABLE` 指向应用包内 `Contents/MacOS/SaveHub`；实际解包目录以构建输出为准。完成 DMG 挂载、拖入 Applications、首次启动、游戏目录访问、存读档、退出重启和旧资料库读取的人工验证。使用 `shasum -a 256` 记录最终 DMG / ZIP 摘要。

首次打包需要联网：electron-builder 会从 GitHub 下载 Electron 运行时、DMG 构建工具和 7zip，之后使用本机缓存。

`build.mac.identity` 设为 `"-"`，打包时做 **ad-hoc 签名**。Apple Silicon 要求可执行代码带有效签名；未签名时 electron-builder 修改包内容后签名会失效（`codesign --verify --strict` 报 `code has no resources but signature indicates they must be present`），下载后带隔离属性打开会提示“已损坏，无法打开”。ad-hoc 签名后包签名有效，其他 Mac 首次打开会提示“无法验证开发者”，可在“系统设置 → 隐私与安全性”中选择“仍要打开”。用 `codesign --verify --deep --strict --verbose=2 release/<版本>/mac-arm64/SaveHub.app` 确认签名有效。

ad-hoc 签名不等于 Developer ID 签名或公证，`hardenedRuntime: true` 本身也不代表已签名或公证。配置正式签名时**必须删除 `build.mac.identity: "-"`**，否则它会覆盖 `CSC_NAME` / `CSC_LINK` 继续做 ad-hoc 签名。面向其他用户分发前，按 [electron-builder v26 签名文档](https://www.electron.build/v26/docs/features/code-signing/) 配置 Developer ID 签名及公证，并在其他 Mac 验证系统认可情况；凭据放入本机安全存储或 CI Secret，不写入仓库。Windows 签名也尚未配置，现有 `signExecutable: false` 需要在实施正式签名时一并调整。

`pnpm test:portable` 仅用于 Windows；`pnpm audit:release` 已支持 Windows 与 macOS arm64 ASAR 布局。运行 `node scripts/test-package.mjs` 验证当前平台的实际应用包，`node scripts/test-apfs.mjs` 只在 Apple Silicon 上验证两种 APFS 大小写模式。

## 9. 本地交付与远程发布

### 9.1 本地交付

满足源码检查、实际包验证和摘要审计后，可交付安装版或便携版，同时提供发布说明、对应摘要和验收记录。若交付解包版，应把整个 `win-unpacked` 一起提供或整体压缩，不能只发送内部 EXE。

最终交付目录至少应能回答：这是哪个版本、对应哪份源码、用户运行哪个文件、通过了哪些验证、哪些平台或安装流程尚未验证。传输后重新计算收到文件的摘要，与原始清单比较。

### 9.2 GitHub Release（配置远程仓库后）

当前仓库没有 remote，且本机未安装 GitHub CLI；以下是未来发布步骤，不表示已经上传。先配置真实仓库地址、安装并登录 `gh`，确认所用账号对目标仓库有发布权限。不要把示例地址当成真实远程地址。

发布前提交并审核本次源码和文档，确保构建时的提交就是准备打标签的提交。`release/` 被忽略，通过 Release 附件上传发行文件；无需强行把 EXE 加进 Git。

检查仓库、提交及账号：

```powershell
git remote -v
git status --short
git log -1 --oneline
gh auth status
```

在确认当前提交与已验收包一致、工作区干净、`origin` 为正确仓库后，创建新标签并推送：

```powershell
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$tag = "v$($pkg.version)"
git tag -a $tag -m "SaveHub $($pkg.version)"
if ($LASTEXITCODE -ne 0) { throw '创建标签失败；先检查是否已有同名标签。' }
git push origin HEAD
if ($LASTEXITCODE -ne 0) { throw '推送源码失败。' }
git push origin $tag
if ($LASTEXITCODE -ne 0) { throw '推送标签失败。' }
```

同名标签已经存在时先核对其提交，不强制覆盖。若某一步中断，从第一个未完成步骤恢复。确认对应 CI 结果后，上传**同一批已验收文件**；如改用 CI 生成的包，重新对那批文件做摘要与发行验收，不能沿用本地包的摘要。

以下命令会真正公开创建 Windows Release，执行前先完成上述工作，并准备好该版本的 `发布说明.md`：

```powershell
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
$tag = "v$($pkg.version)"
$releaseDir = (Resolve-Path -LiteralPath $pkg.build.directories.output).Path
$releaseAssets = @(
    (Join-Path $releaseDir "SaveHub-$($pkg.version)-win-x64.exe")
    (Join-Path $releaseDir "SaveHub-$($pkg.version)-Windows-x64-portable.exe")
    (Join-Path $releaseDir 'SHA256SUMS.txt')
)
$notesFile = Join-Path $releaseDir '发布说明.md'
foreach ($file in ($releaseAssets + @($notesFile))) {
    if (-not (Test-Path -LiteralPath $file -PathType Leaf)) { throw "缺少发布文件：$file" }
}
gh release create $tag @releaseAssets --verify-tag --title "SaveHub $($pkg.version)" --notes-file $notesFile
if ($LASTEXITCODE -ne 0) { throw 'Release 创建或上传失败，先检查远端状态再继续。' }
gh release view $tag
```

`--verify-tag` 要求远端标签已存在，`--notes-file` 读取完整 Markdown 发布说明；需要先人工检查页面时可额外加 `--draft`，检查后在 GitHub 发布。参数以 [GitHub CLI 的 release create 文档](https://cli.github.com/manual/gh_release_create) 为准。多行发布说明通过文件传递，不拼成一段 shell 转义字符串。

上传后检查版本、标签、附件名称和大小，再下载附件校验 SHA-256。若 `SHA256SUMS.txt` 同时包含未上传的解包目录文件，下载用户只核对实际下载项；如需提供独立下载清单，可另建只包含公开附件的摘要文件，并保留完整本地审计清单。Mac 包只有实际完成构建与验证后才加入对应发布资产。

项目没有应用内自动更新器。发布新 EXE 或 GitHub Release 不会自动更新用户已安装的应用，需要用户关闭旧版并安装或打开新版。

## 10. CI 的现有能力与边界

PR 在 Windows 执行 lint、format、契约、类型/构建、单测及 smoke/恢复点 E2E。主分支和标签增加 Windows x64 / macOS arm64 的源码与实际包完整回归、打包、便携版/APFS 检查、摘要及 ASAR 审计；失败证据用 always() 上传。只有标签 draft Release 作业授予 contents: write，未增加 Intel Mac 任务。工作流已配置不等于远端已成功执行。

## 11. 资料库备份、升级与回退

升级前关闭应用，在“设置与关于”确认资料库路径，备份整个目录。内容包括 `library.json`、`library.json.previous`、`vault/` 和可能存在的 `transactions/`；只备份安装目录或 EXE 不包含游戏存档备份。

1.1.5 保持磁盘格式版本号，但引入 5/15 双队列默认保留策略和修改时间。0 表示不保留；旧 maxRestorePoints 不沿用。旧记录缺少 updatedAt 时以创建时间初始化，修改时持久化。升级会在恢复事务后执行有效上限整理，详见 README 的保留规则。

回退程序时，保留新旧发行目录，关闭当前进程后启动经验证的旧版本。程序回退不等于游戏当前进度回退，也不会自动撤销新版期间的存读档操作。未来若引入不兼容数据格式，必须先制定迁移及回退策略，不能根据当前布局推断旧版本永远可读新数据。

保留完整导出文件夹才能携带 `.savehub-exports` 中的名称、备注、标记与校验清单。导出不是整个应用资料库的镜像备份：游戏配置、主题和未导出的其他记录仍需要资料库备份。

## 12. 常见问题与本机排错记录

| 现象 | 处理方式 |
| --- | --- |
| `pnpm` / `npm` 找不到 | 先检查 PATH 和 Node 安装；受管运行环境可能有 Node / pnpm 而没有 npm，不必因此重装已有完整依赖 |
| `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY` | 本机曾在 pnpm 包装器检查依赖时遇到；先确认依赖可用及为何要求重建，不直接设置 `CI=true` 强制清空模块目录；可按下方本地入口执行 |
| Electron 下载的 `RequestError` / `AggregateError` | 检查网络及下载限制；本地正确版本已经安装时，可按第 6.3 节传入 `electronDist` |
| builder 依赖收集阶段 `ERR_SQLITE_ERROR` | 本机受限环境中出现过；保留错误和执行位置，在具备正常缓存访问权限的终端重试同一步，不随意更改版本或系统目录权限 |
| GUI 报 `FATAL`、`install_dir_access` 或 `ALL APPLICATION PACKAGES` 访问错误 | 本机工具沙箱曾阻止 Electron 启动；区分环境启动失败与测试断言失败，使用正常权限的桌面终端验证；不通过关闭 Electron 沙箱或批量放宽 ACL 处理 |
| `ELECTRON_RUN_AS_NODE` 导致没有窗口 | 清除本轮启动环境中的该变量；开发和测试脚本已有处理 |
| 5173 被占用 | 检查已有 Vite 进程；停止本项目重复服务后重试 |
| 打开后仍是旧按钮 / 旧版本 | 检查运行的是哪个 EXE、`SAVEHUB_TEST_EXECUTABLE` 是否遗留、是否只更新了 `dist/` 而未打包 |
| `Packaged source differs` 或 ASAR 缺少资源 | 当前源码 / `dist/` 与包不匹配；针对正确版本重新构建打包，不能改摘要使其表面通过 |
| 只有旧成功报告、新测试却失败 | 核对时间、退出码和被测程序；旧 JSON 不代表本轮结果 |
| NSIS 压缩长时间无新输出 | 查看构建是否仍运行；中间小文件不代表最终包损坏，等待进程结束后核对退出码和完整输出 |
| CI 中 `dist:*` 末尾报 `GitHub Personal Access Token is not set ... "GH_TOKEN"`，但安装包已生成 | electron-builder 26 在 CI（非 Pull Request）未指定 `--publish` 时隐式发布；`pack:*` / `dist:*` 已显式带 `--publish never`。保持只构建不发布，不要为绕过报错配置 `GH_TOKEN` 或提升 `contents` 权限；确需发布 Release 时按第 9、10 节单独设计发布步骤 |
| 卸载或更换便携 EXE 后资料仍在 | 资料库与程序分离，这是当前设计；到设置中查看真实路径 |

依赖完整时，可直接执行与项目脚本对应的本地入口，避免包管理器包装器的附加行为。以下命令互相独立，按需要选择，并检查各自退出码：

```powershell
node scripts/dev.mjs
node node_modules/typescript/bin/tsc --noEmit
node node_modules/vite/bin/vite.js build
node node_modules/electron/cli.js .
node --test tests/*.test.mjs
node scripts/smoke.mjs
node scripts/interactions.mjs
node scripts/deletion-interactions.mjs
node scripts/portable-smoke.mjs
node scripts/audit-release.mjs
```

直接运行 Vite 入口不会附带类型检查；GUI 入口仍需要先构建、选择正确的程序和隔离资料库。`electron/cli.js .` 与 `pnpm start` 一样会读取生产页面，不能忽略第 4.2 节的环境设置。

本机发行时曾由工具权限审核批准在受限沙箱外完成 GUI 测试和打包。自动审批额度耗尽或工具调用被拒绝属于执行环境问题，不是应用测试失败；保留已完成证据，环境恢复后继续未完成步骤，不重复覆盖已确认的修改。

## 13. 中断恢复与最终检查

恢复工作先确定停在哪里：

```powershell
git status --short
git diff --stat
git diff --check
Get-ChildItem -LiteralPath test-results -Filter 'run.json' -Recurse -File |
    Select-Object Name,Length,LastWriteTime
$pkg = Get-Content -LiteralPath package.json -Raw | ConvertFrom-Json
if (Test-Path -LiteralPath $pkg.build.directories.output) {
    Get-ChildItem -LiteralPath $pkg.build.directories.output -File |
        Select-Object Name,Length,LastWriteTime
}
```

先阅读上一轮日志、测试报告及 Git diff；命令调用中断不等于进程已经结束。确认原进程是否仍在运行、是否已有退出码或完整最终文件。单独的文件时间或非零大小不足以证明打包成功，还需包内一致性、摘要和启动结果。

对已经完成且源码未变的检查保留证据；只有状态无法判断、输入代码变化或存在未解决失败时才重跑对应步骤。不要清空整个 `release/`、`.local-data/` 或重新实现已完成的功能。

一次版本交付应保留以下结论：

- 版本号、输出目录和源码提交一致；待发布功能与发布说明一致。
- 类型检查、核心测试、生产构建和相关 GUI 检查已通过；代码有变化时重新验证受影响部分。
- 实际交付程序经过运行验证，报告记录正确的程序路径；安装流程和各平台的未验证项明确列出。
- Windows ASAR 与当前源码 / 前端产物一致，最终文件 SHA-256 匹配；Mac 包单独记录其验证结果。
- 摘要、发布说明、截图和验收证据已归档，旧版本与用户资料库保留。
- 对外发布时，标签指向验收源码，附件可下载且摘要一致；本地交付、CI 产物和公开 Release 的状态分别如实记录。
