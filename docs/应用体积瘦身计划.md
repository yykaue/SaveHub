SaveHub 打包体积瘦身计划
======================

制定日期：2026-11-06（Asia/Shanghai）。检查基于本地 `main` 分支 `e616e63`、当前打包配置和 `release/1.1.5` 下的 Windows x64 制品。本次仅制定计划；未实施配置调整、修改业务源码或重新打包。

**建议从发行包压缩方式与运行时语言资源入手。业务代码和资源仅占解包目录约 0.30%，压缩前端代码无法解决百 MB 级的体积问题。** 保留 Electron、现有业务实现和离线使用方式，先用同一份源码制作对照包，再按单一变量验证每项优化。

下文 MB 均为十进制，即 1 MB = 1,000,000 字节；MiB 为 1,048,576 字节。下载大小与解包大小分别统计。

当前使用 Electron 45.1.0、electron-builder 26.18.0。已经具备的措施包括：

- `build.files` 使用包含清单；实际 ASAR 中没有 `node_modules`、测试、文档、历史发布目录或包管理器缓存。
- 前端已使用 Vite 生产构建，`sourcemap: false`；当前 `dist` 共约 0.477 MB，旧制品中的 `dist` 约 0.471 MB。
- 已启用 ASAR；它将文件合并为归档，本身不进行压缩，继续开启即可。[ASAR 官方说明](https://github.com/electron/asar/blob/main/README.md)
- Windows 仅打包 x64，macOS 配置仅打包 arm64，没有把多个架构合并进当前 Windows 安装包。

现有制品中的多个文件与当前工作区文件的 SHA-256 不一致，前端产物名称也不同。因此，这组数据只能用于识别体积来源，不能直接作为当前代码优化后的验收对照。不能沿用旧制品的审计成功记录来证明新制品正确。

**实施顺序与收益边界**

| 顺序 | 工作                                           | 可期待的收益                                                | 采用条件                                                     |
| ---- | ---------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------ |
| P0   | 为当前提交重建原配置对照包，建立体积与哈希清单 | 得到可比较的基线                                            | 所有实验使用同一份业务源码、依赖锁文件、工具版本和架构       |
| P1   | A/B 验证 `nsis.differentialPackage: false`     | 可能缩小安装版；不会直接缩小便携版或解包目录                | 不存在使用差分更新的现有链路，且安装、覆盖升级、卸载回归通过 |
| P2   | Windows 单独试验 Chromium 语言包包含清单       | 按现有文件可减少解包体积 48.83 MB，约 13.0%；下载收益需实测 | 中英文功能不变，系统语言与原生控件兼容性验证通过             |
| P3   | 收紧构建期文件与跨平台资源的包含范围           | 仅 KB 至不足 0.5 MB 量级的解包收益                          | 每个排除项都确认无运行时引用，并同步维护严格的制品审计       |
| P4   | 自动生成体积报告并接入发布检查                 | 防止后续意外增大                                            | 独立统计安装版、便携版、解包目录和 ASAR                      |

建议优先完成 P0、P1；P2 是空间收益最大的候选，但必须单独验证。P3 收益很小，不作为首轮必须完成的优化。

**P0：统一比较基线**

1. 固定当前提交和锁文件，保持 Electron 与 electron-builder 版本不变。原配置包与候选包放在不同的实验输出目录，保留现有发布制品。
2. 记录源码提交、Node/pnpm/打包器版本、有效配置、压缩相关环境变量、构建耗时，以及所有产物的字节数和 SHA-256。
3. 输出解包目录按文件和目录聚合的大小、ASAR 文件清单，以及 ASAR 内所有运行时文件的内容哈希。
4. 对照包先通过现有检查。实验不混入依赖升级、功能修复、代码重构或版本号调整。

**P1：验证 NSIS 压缩布局**

目前没有在 `package.json`、`electron/`、`src/`、`shared/` 中发现 `electron-updater` 或 `autoUpdater` 接入。打包器默认仍会生成支持差分下载的安装包；关闭该选项会失去差分下载支持，因此应先核对实际发布、更新链路。[electron-builder v26 的 NSIS 配置](https://www.electron.build/v26/docs/api/app-builder-lib.interface.nsisoptions/#differentialpackage)

本地安装的打包器实现显示：差分归档使用 1 MB 字典并关闭 solid 压缩；便携版不走这一分支。因此，在没有现有差分更新需求的前提下，试验关闭安装版差分支持具有针对性。

- 只调整实验配置中的 `nsis.differentialPackage`，其余选项保持不变。
- 对比安装版字节数、构建时间、安装时间和安装后的文件内容。
- 当前安装版比便携版大约 11.03 MB，这只是值得调查的线索，不是关闭选项后保证节省的数值。
- 不通过删除独立 `.blockmap` 文件来宣称 EXE 瘦身；需要比较重新生成的 EXE 本身。
- 如发现现有更新链路依赖差分下载，保留原设置；如收益很小或安装明显变慢，放弃该项。

不把单独设置 `compression: "maximum"` 作为主方案。本地 26.18.0 的 `compute7zCompressArgs` 对非 ZIP 归档在 `normal` 与 `maximum` 下均使用 `-mx=9`；官方也说明 `maximum` 通常不会带来明显体积差异。发布时记录环境变量覆盖，避免比较条件不同。[压缩选项说明](https://www.electron.build/v26/docs/configuration/#compression)

**P2：有条件地精简运行时语言包**

应用业务语言为 `zh` 和 `en`，来自 `shared/locales` 与前端国际化配置。Chromium 的 `locales/*.pak` 是另一组运行时资源，不能因为业务界面只有中英文，就认定其他语言包完全没有可见影响。

先仅在 Windows 实验配置中设置 `build.win.electronLanguages`，候选保留：`en-US`、`en-GB`、`zh-CN`、`zh-TW`。保留繁体中文运行时资源用于兼容系统环境，不新增业务语言。使用打包器提供的选项，不手工删除已发布包中的文件。[语言资源配置说明](https://www.electron.build/v26/docs/configuration/#electronlanguages)

基于现有制品的精确计算：保留 4 个文件共 2,369,371 字节，排除另外 51 个文件共 48,825,855 字节。其余内容相同的情况下，解包目录从 375.37 MB 降到约 326.54 MB。**这不代表安装包或便携版也会减少 48.83 MB**，压缩后收益必须分别测量。

需要覆盖简体中文、繁体中文、英文和至少一种非中英文系统语言环境，检查首次启动、界面切换、文件/目录选择器、原生提示和输入行为。命令行语言覆盖只能作为补充，不能替代系统语言环境验证。Electron 的应用区域设置由 Chromium 取得，发行包仍需携带语言资源。[Electron 区域设置说明](https://www.electronjs.org/docs/latest/api/app#appgetlocale)

如果原生文案或其他系统语言体验发生了不允许的变化，补回受影响的语言；若要求所有系统语言行为完全保持现状，就跳过此项，不强制全局 `--lang` 来规避差异。中文、英文业务字典与日期格式实现均保留。

macOS 不直接复用 Windows 的节省量或删除规则。本轮先保持 macOS 配置不变；后续必须在真实 arm64 制品中检查 `.lproj`、原生菜单和系统语言行为，再决定是否使用平台专属包含清单。

**P3：只处理已证明无用的少量文件**

- `shared/contracts.ts` 为构建期类型契约，可在确认所有引用均在构建时消除后排除；当前工作区约 7 KB。`.d.ts` 已由打包器自动排除，不能重复计算收益。
- Windows 窗口运行时明确使用 `icon.ico`。可核对 `icon.png` 是否还被其他路径引用，再考虑仅从 Windows 的 ASAR 中排除；当前 PNG 为 318,422 字节。macOS 及源码中的图标资源保留。
- 解包目录含约 111 KB 的 `default_app.asar`，可核实它在正常入口、无效参数和启动失败路径下是否仍会被使用；没有充分证据时保留。

当前 `scripts/audit-release.mjs` 会遍历 `shared`，并要求 PNG/ICO 同时存在。如果调整包含清单，需将审计改为明确列举构建期排除项，并继续对所有运行时文件断言存在、逐项校验 SHA-256；不能改成“文件存在才检查”。

**业务不变的验收方式**

| 验收维度       | 通过标准                                                                                                         |
| -------------- | ---------------------------------------------------------------------------------------------------------------- |
| 业务文件一致性 | P1/P2 对照包与候选包的 ASAR 内业务文件路径和内容哈希一致；只有约定的外部打包资源发生变化                         |
| 存档与数据格式 | 创建、读取、导入导出、收藏、保护、回收站、恢复点、保留策略、事务恢复和日志行为均通过现有回归；旧资料库可继续打开 |
| 界面与系统集成 | 主题、中英文切换、图标、原生选择器、中文/空格路径、离线启动和单实例行为通过                                      |
| 安装与便携运行 | 安装、覆盖升级、路径选择、卸载保留数据、便携版启动与退出、数据位置均保持现有行为                                 |
| 性能与体积     | 分别记录下载字节数和解包字节数；对照与候选各重复测量启动/安装耗时，异常退化需复核，不能用偶然单次结果决策        |
| 制品完整性     | 运行时必需文件、许可证、图形与软件渲染组件完整；重新生成校验和并通过制品审计                                     |

复用现有校验命令：`pnpm lint`、`pnpm format:check`、`pnpm check:contracts`、`pnpm test`、`pnpm build`。候选确定后运行 `node scripts/test-package.mjs` 的完整打包应用回归、`pnpm test:portable`、`scripts/test-installer.ps1`，再运行 `pnpm checksums` 与 `pnpm audit:release`。测试使用隔离资料目录；实验输出目录需正确传给测试与审计脚本，防止误测旧包。

语言裁剪增加针对运行环境的兼容检查。纯打包配置调整无需新建重复验证业务实现的单元测试；已有业务回归用于确认交付物行为一致。

**体积报告与完成标准**

后续增加 `scripts/report-package-size.mjs`，输出机器可读 JSON 和简洁报告，接入 `.github/workflows/build.yml` 的打包任务。报告包括制品、运行时分类、ASAR 分类、语言列表、源码与工具版本。阈值按平台、架构和目标分别设置。

首轮先记录，候选验证完成后再固定基线；建议相对已验证基线上涨超过 `max(2 MB, 2%)` 时触发体积检查失败。正常的运行时升级可在复核报告后更新基线。

实验按“原配置、仅 P1、仅 P2、P1+P2”的顺序比较，只有每项独立通过后才组合。P3 如实施则另做一次差异审计。交付应包含体积前后对照、有效配置、文件变更清单、业务一致性证据及回退说明。任何兼容性失败都回退对应选项，保留其余已验证的收益。

不预先承诺压到 100 MB 以下。当前能够量化的是语言包的约 48.83 MB 解包空间候选收益；下载大小与 NSIS 调整收益由同源 A/B 制品决定。在保留完整 Electron 运行时的前提下，本轮没有证据支持把离线制品压到几十 MB。

本轮不安排 Electron 降级、更换 Tauri/WebView2、定制裁剪 Chromium、UPX 处理运行时、删除 ICU/FFmpeg/图形 DLL/许可证，或改成联网下载运行时的安装器。这些操作涉及兼容性、架构或分发行为变化，不适合作为本次保守瘦身的实施范围。清理本地 `node_modules`、`.pnpm-store` 和旧 `release` 只能释放开发机器空间，当前打包包含清单已将它们排除，不会缩小发布 EXE。
